The second release candidate for 1.0.0. Everything in
[v1.0.0-rc.1](https://github.com/axlaser/claude-statusline/releases/tag/v1.0.0-rc.1) still
applies — one Rust binary replacing the three per-platform script trees, rendering
identically on all of them. This candidate fixes the way that binary gets **installed**.

**If you installed rc.1, upgrade.** Three defects between rc.1 and here could each leave an
install broken, and one of them could take a working script installation down with it.

## Installing

```bash
curl -fsSL https://raw.githubusercontent.com/axlaser/claude-statusline/dev/install/install.sh | bash -s -- --pre
```

```powershell
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/axlaser/claude-statusline/dev/install/install.ps1))) --pre
```

Both fetch the installer from `dev`, which is where prereleases are cut from — the `install/`
directory does not exist on `master` until 1.0.0 merges, and a stale URL there fails silently:
`curl -fsSL` prints nothing on a 404 and `bash` exits 0, so it looks like the installer ran
and did nothing. The PowerShell form is longer than the plain one-liner because `irm | iex`
cannot pass arguments.

## Fixed since rc.1

**Every Linux install was refused before anything downloaded.** The installer probes whether
`stat` speaks the GNU or BSD dialect. On GNU coreutils `-f` means `--file-system`, so the
probe ran both halves and read back a filesystem report concatenated with a uid — which the
ownership gate then rejected as "owned by someone else". The dialect is now detected with a
positive test rather than the exit code of a malformed invocation.

**The stable install channel did not work on PowerShell 7.** Resolving the latest release
read `BaseResponse.ResponseUri`, which exists on Windows PowerShell 5.1 and does not exist at
all on PowerShell 7 — it rebuilt `Invoke-WebRequest` on `HttpClient`, where the redirected
URI lives somewhere else entirely. On 7 the request succeeded, the tag came back empty, and
the install aborted with "Could not resolve the latest release". Both spellings are now read.
`--pre` was never affected, which is why this went unnoticed.

**A binary that could not launch passed the check meant to catch it.** `$LASTEXITCODE` is
only written by a process that actually starts, so a binary that failed to launch — wrong
architecture, a truncated download, antivirus interference — left the *previous* command's
success code in place. The self-check gate read that stale zero, concluded the binary was
fine, and went on to repoint `settings.json` at it and delete a migrating user's scripts:
exactly the sequence that gate exists to prevent. Every such check now distinguishes "it
answered no" from "it never ran", and a binary that cannot start is reported as that rather
than as one that rendered wrongly.

**A missing stable release read as a download failure.** With no stable release published,
`/releases/latest` redirects to the releases index rather than to a tag, so the installer
resolved the literal string `releases`, built a download URL from it, and reported the
resulting 404 as "Download failed" — naming neither the cause nor the fix. It now recognises
that there is no stable release and says so.

## Also in this candidate

- **A finished subagent row disappears after 30 seconds again.** When the tasks feed is
  unavailable and the status line falls back to reading transcripts, the row had been
  outliving its linger by the full three-minute staleness window. The same stored record also
  restores the skip that stops every subagent transcript being re-read on every refresh.
- **A stalled `git` can no longer hold a refresh open.** The child is killed at a two-second
  deadline, and the read of its output is bounded separately — killing a process closes only
  its own handle on the pipe, and anything `git` spawned keeps the rest open.
- **`settings.json` is safer to hold.** A file that is valid JSON but not an object is now
  refused instead of replaced, and a symlinked `settings.json` is written *through* rather
  than replaced with a regular file.
- **`STATUSLINE_DEBUG=1` explains more.** A payload that fails to parse now logs why — the
  one user-visible failure the status line has, and previously the one that logged nothing.

## What is now tested

The installers had no execution coverage at all. Every check on them was a static inspection
of the script text, which is how three defects in their control flow reached a release
candidate.

CI now runs all four installer scripts on Linux, macOS, and Windows under **both** Windows
PowerShell 5.1 and PowerShell 7 — install, re-install, uninstall, and the stable channel —
plus an upgrade from a simulated script installation that asserts no entry survives pointing
at a script the same run deleted.

## Verifying the download

The installer verifies the SHA-256 before placing anything, and there is no path that skips
it:

```bash
sha256sum --check --ignore-missing checksums.txt
```

Every artifact also carries a build-provenance attestation. The installer checks it
automatically when the [GitHub CLI](https://cli.github.com) is present — no `gh auth login`
needed, since the bundle ships as a release asset and verifies offline:

```bash
gh attestation verify claude-statusline-<target> \
  --repo axlaser/claude-statusline \
  --signer-workflow axlaser/claude-statusline/.github/workflows/release.yml
```

## Reporting a problem

The status line fails silently by design — it never writes to stderr and always exits 0,
because anything else breaks Claude Code's UI. A fault therefore reaches you as an absent
status line and nothing else:

```bash
~/.claude/bin/claude-statusline self-check   # exits 0 if the renderer is sound
STATUSLINE_DEBUG=1                           # then read ~/.claude/statusline-debug.log
```

A `panic caught in subcommand` line in that log is always worth reporting.
